ASSUMPTIONS FOR MILESTONE III


THE APPLICATION

- The application is a web app built with Streamlit (Python). It runs as a website and talks only to the database hosted on Aiven, never to localhost. My TA confirmed that a website acting as an interface to a cloud-hosted database counts as a web-based app.
- The app has a sidebar menu with one page for each of the 10 features in the spec, in the same order as the spec.


HOSTING THE DATABASE

- The database is hosted on a free Aiven MySQL 8.4 server. I chose Aiven over db4free.net (the example in the spec) because it is more reliable.
- Aiven only accepts encrypted connections. The app checks the server against Aiven's CA certificate (ca.pem). The certificate is public, since it only proves the server is really Aiven's, so it is included with the code. The password is not: it is kept in a .env file that is never committed.
- The Milestone II dump was imported into Aiven unchanged, except that DEFINER=root@localhost was removed from the v_user view. Aiven has no root user and doesn't let my user create objects on another user's behalf, so the import would fail otherwise. Without it, the view belongs to my Aiven user.
- After the import, every table had the same number of rows as its Milestone II CSV file (e.g. 8,574 properties, 4,551 developments, 31,649 amenity rows).


USERS AND REVIEWS

- There is no login or password, because the spec only asks for users to register with their email. To add a review, a user types the email they registered with.
- At least one area of focus is required when registering, since the spec lists it as part of registration.
- Age is not typed in. It is worked out from the birthdate by the v_user view (as in Milestone I), so it never goes out of date.
- Registering saves the user and their areas of focus as one transaction, so either all of it is saved or none of it is.
- The rules are enforced by the database, not the app. The UNIQUE, CHECK and FOREIGN KEY constraints from Milestone I reject a taken email or username, an invalid email, a rating outside 1-10, a second review of the same project, or a review from an unregistered email. The app catches these MySQL errors and shows a friendly message instead.
- Reviews show the reviewer's username, not their email, so other visitors can't see people's emails.
- An empty review text is stored as NULL, like the sample reviews without text from Milestone II.


DEFINITIONS USED IN THE ANALYTICS PAGES

The spec uses some terms without defining them. These are the definitions I used:
- Price = down_payment + remaining_amount ("Cash required now" + "Remaining with developer"), as stated in my Milestone II assumptions.
- Price per m2 = price / area_sqm, also as stated in Milestone II. Every listing has an area, so none are left out.
- Resale amount = the total price of all the listings counted.
- Gain over market value = gain_amount, the site's own "Your gain vs. current market price". I checked that it equals market price - price - the buyer's 1.25% fee, so it doesn't need to be recalculated.
- Discount over market price = (market_price - price) / market_price, as a percentage. E.g. a unit worth 10M on the market that is offered for 8M has a 20% discount. A percentage lets cheap and expensive units be compared fairly.
- Age of contract year = the current year - contract_year. E.g. a contract from 2022 is 4 years old in 2026.
- Installment price = installment_amount (the amount of each installment).

Ranking projects by gain
- For "top 10 projects with the highest gain over market value", projects are ranked by their average gain per listing, not the total gain of all their listings. A total would mostly repeat the "highest resale inventory" ranking, because a project with many listings adds up a large total even if each unit is a weak deal. The average shows which projects actually give buyers the best gain.

Ranking projects
- When two projects tie in a top 10 list, they are ordered by project name, so the list is always in the same order.
- A project is identified by its development_id, not its name, since the same project name can exist in two areas (as in Milestone I). Each row shows the project's area to tell them apart.
- Because the gain list uses an average, a project with very few listings can reach the top just because one of its listings has a large gain (or a typo in its market price). With no minimum, 9 of the top 10 apartment projects had a single listing, so the list was really ranking single units, not projects. So the gain list only ranks projects with at least 3 listings by default. 3 is the smallest number where one unusual listing can't decide the average on its own (with 2, a project with one 1M gain and one 41.5M gain averaged 21M). The minimum is a control on the page, so it can be changed (e.g. set to 1 to see every project). The number of listings is shown next to each average.
- The minimum only applies to the gain list. The inventory and resale amount lists are totals, so they don't have this problem.

Top 5 developers
- A developer's listings are the listings in all of their development projects.
- Projects with no developer listed are left out of this page.
- Developers are counted by their name in the developer table. The top developers' different spellings were merged first (see "Changes to the Milestone II data" below).


CHANGES TO THE MILESTONE II DATA

Merging the spellings of the top developers
- Sellers type the developer name themselves, so the same developer appears under many spellings: English and Arabic ("Palm hills" / "بالم هيلز"), typos ("Palm hilles", "بالم هيبز"), and with extra words ("شركة بالم هيلز", "Palm Hills Development (PHD)"). Milestone II only merged names that differ in case, spacing, accents or Arabic letter forms, so the Top 5 developers page showed Palm Hills and Mountain View twice each.
- I merged the spellings of the 18 developers that end up near the top: Talaat Moustafa Group, Palm Hills Developments, Mountain View, Madinet Masr, Tatweer Misr, Hyde Park Developments, Al Ahly Sabbour, Ora Developers, Orascom Development, City Edge Developments, Al Marasem, IL Cazar Developments, Misr Italia Properties, Amer Group, Hassan Allam Properties, SODIC, Taj Misr and PRE Developments. Each one is stored under its usual English name.
- A spelling was only merged when it clearly is that developer: any spelling or language, with or without words like "شركة" or "Developments", or with one of its projects or its owner's name added.
- These were left out on purpose:
  - different companies with similar names (Orascom Development is not Ora Developers, Arkan Palm and Palmier are not Palm Hills, Mountain Valley is not Mountain View)
  - subsidiaries (e.g. "one of Talaat Moustafa's companies") and joint ventures (e.g. "Al Ahly Sabbour and Founders")
  - names on their own that could be more than one company ("صبور", "عامر")
- Smaller developers were not merged, so they may still appear under more than one spelling.
- The merge was done by merge_developers.py, which lists every spelling that was merged. It runs as one transaction, so either everything is merged or nothing is. Before saving, it was run as a dry run that showed the result and then undid it.
- Result: the developer table went from 2,618 to 2,412 rows (206 duplicate spellings removed), and 1,681 developments now belong to these 18 developers. No developments, properties or other rows were added or removed. The top 5 changed from طلعت مصطفى, بالم هيلز, Palm hills, Mountain View, ماونتن فيو to Talaat Moustafa Group (870 listings), Palm Hills Developments (837), Mountain View (528), Hyde Park Developments (316) and Madinet Masr (291).
- Because of this, the developer and development tables on the server no longer match the Milestone II CSV files exactly. The Milestone III database dump has the merged data.

Properties by area, type and contract year
- Each of the three filters is optional. An empty filter means "any", and with no filters every listing is shown.
- Listings with no contract year only appear when no contract year is picked.

Averages by area and project
- There is one row per area and development project.
- An area filter is optional. With no area picked, every area and project is shown.

Searching by price and amenities
- The price range includes both ends (a listing at exactly the maximum price is included).
- The price range starts at the cheapest and most expensive listing in the chosen area, so nothing is left out until the user changes it.
- A listing must have all of the chosen amenities, not just one of them.
- The amenity list leaves out 2 entries that are really pieces of a listing's description that ended up in the amenities in Milestone II (each appears on only one listing). The 8 real amenities are each on hundreds or thousands of listings. The 2 entries are still in the database. They are only hidden from the list.

Missing values
- 298 listings have no market price, so they have no gain or discount. 707 listings have no contract year. MySQL's AVG() skips NULL values, so these listings are left out of those averages only, and still count everywhere else.
- Each page shows the number of listings next to its averages, so it's clear what each average is based on.
